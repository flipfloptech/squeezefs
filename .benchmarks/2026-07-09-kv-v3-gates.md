## Micro method (honest notes)

§8 prescribes criterion medians vs a `pre_kv_v3` baseline "captured
immediately before K6a". That baseline was never captured (no
`target/criterion` state existed on this box). The v2 metadata path is
untouched since the committed reference (its own suites pin
byte-identical behavior), so per the orchestrating decision the v2-path
rows (`meta_lv_metadata/*`) were measured **fresh on this binary** and
serve as the baseline; the KV-path rows (`kv_meta_metadata/*`, added by
K7 as exact trait-path mirrors — same op sequences incl. `destroy_inode`
against a mounted `KvMetaBackend`) are compared against them. A
`--save-baseline pre_kv_v3` criterion snapshot is saved at the final
commit for future regressions.

Machine-state sensitivity, stated: run-block ordering flips single-block
results by ±15 % (frequency/thermal state), so the gated statistic is
**interleaved same-thermal pairs** (v2 then KV back-to-back, ×5, Tctl
62–65 °C, 16-core cap). Pre-crash uncapped pairs measured KV 84.1 vs v2
96.9 µs — same verdict, wider spread.

Context rows (final binary, capped): `set_get_xattr` v2 ~99.8 µs vs KV
~27.0 µs (−73 %); `readdir_page_100_of_1k` 34.6 µs (the §5.1 streaming
step); `kv_tree/point_lookup_hot_100k` ~0.72–0.76 µs;
`insert_48b` ~3.9 µs; `point_lookup_cold_demand_page` ~83.6 µs — the
§4.4 "read amplification, honest accounting" cold-leaf number, as
designed.

## Gate-run bugs found & fixed on this branch (tests-first each)

The §8 rows did their job: six real defects surfaced; each was
root-caused and fixed here with a red-first regression pin in
`tests/kv_scale_tests.rs` (plus the R10 storm recalibration):

1. **Tombstone-desert scan cliff** (`68d4b4b`, pin `5aa0ec8`):
   `NodeSnapshot::next_live` walked live-ward with no range bound, so the
   ≤ 256-key dentry/xattr chain probes behind every lookup/create/unlink
   fold-walked the whole tombstone desert a create/unlink storm leaves in
   the leaf until compaction. Post-storm lookup: 323 ns → 339 µs
   (~1000×); pinned at 178× p50 in debug; bounded scans measure ~2–4×
   (in-window folds — inherent CoW-until-compaction cost).
2. **§4.6 pt 1 threshold writeback never woke the task** (`6f70347`,
   pin `c1fe571`): commits enqueued maintenance at a bset-worth of open
   delta but nothing woke the checkpoint task, so deltas ballooned for a
   whole 50 ms tick while every commit's RAM apply paid O(delta) for the
   snapshot swap (2.3× worse at a 1 s interval — the smoking gun).
   Fixed with a maintenance-only wake: appends run promptly; barriers
   and ledger records stay on the fixed cadence (a naive every-commit
   wake barrier-storms: measured 262 µs/op at a 5 ms cadence), and the
   ticker is a fixed `interval_at` so sustained wakes cannot starve the
   cadence.
3. **Freeze re-built the whole node index per bset** (`0223109`):
   `RecordIndex::build` re-parses every source and scans all sources per
   emitted entry (O(total × sources)); at the restored per-bset-worth
   freeze cadence that was 36.8 % of the serial create path (perf).
   `extend_with` two-way-merges the ONE new bset in O(existing + new)
   with identical read-path semantics. Serial probe 156 → 50 µs/iter.
4. **Rightmost-separator replay rejection + descend spin** (`bfcb34a`,
   pins `9e8c481`): (a) a rightmost-leaf SMO journals its successor
   pointer record keyed `KEY_SPACE_MAX` — the legal top separator; replay
   ran the content-key guard on it and failed the whole mount loud
   (§4.1 violation), reachable even after clean shutdowns (an SMO
   journaled during the final checkpoint's own flush pass legitimately
   stays in the window). Interior replay now admits the separator domain
   inclusively (deterministic red→green pin). (b) `descend` restarts were
   synchronous spins; they now yield (5.3 M lookups through a 4 s
   SMO-churn storm pin).
5. **SMO swap retired the old route before publishing the new one**
   (`56097b2`): `smo_replace` ran retire → publish → route flip inside
   its lock window; the window is not atomic for latch-free readers, and
   with the SMO task descheduled mid-window under storm load the
   parent's current snapshot kept routing to an already-retired extent
   for milliseconds — readers burned the whole (yielded) 256-restart
   budget on one reason. Diagnosed by the restart-reason tallies now
   carried in the exhaustion error (`[0,0,0,256,0]` — all
   child-retired; ~1/2 of full-1M-storm release runs). Order fixed to
   publish → route flip → retire (eviction cannot re-open the gap:
   `try_evict` is a clean-only CAS). Soak: **4/4** consecutive full-1M
   storms green under the cap.
6. **v3 readdir was stream-always; §4.5 says small dirs keep the cache**
   (`579b24b`): the first paired full-table run measured Readdir
   v3 −23.7 % — the repeat-`read_dir` shape paid two tree range scans
   per call where v2 serves an Arc clone. `dir_entry_cache_v3` now
   snapshots directories ≤ 10 K entries **with their §5.1 cookies**
   (cache-served pages keep the resume contract bit-identically; big
   directories bypass and stream; both caches invalidated at every
   mutation site). Readdir flipped to **+24.2 %** in the final paired
   table.

Also: the R10 ring-full liveness storm was recalibrated (2 KiB payloads
× 300 iterations) because the threshold wakes drain the ring so
aggressively the original shape never parked — reserve-exhaustion
checkpoints advance `reusable_upto` ahead of admission, strictly better
liveness; the storm now re-exercises the park path (which is R10's
point). Perf work #2/#3 plus the two-run snapshot publish and the
alloc-free lookup folds (`cff7024`) closed the micro create row from
+18 % worst-case to −19 %.

### writev03 BROKEN — root-caused: pre-existing, format-agnostic (not a v3 delta)

The one LTP movement (PASS → TBROK) is `writev03`'s **xfs leg**:
`mount(/dev/loopN, …, xfs) failed: EUCLEAN` — kernel-side
`XFS: failed to locate log tail / Corruption detected` during log
recovery of a loop device whose backing file lives on the squeezefs
mount, after earlier fs legs (ext2/3/4) used the same backing file.
Systematic isolation on this box, same LTP build:

| Probe | Result |
|---|---|
| writev03, TMPDIR on tmpfs | PASS 8/8 legs (suite/kernel exonerated) |
| writev03, xfs-only leg on v3 | PASS |
| writev03, full leg sequence on **v3** | BROKEN 3/3 runs |
| writev03, full leg sequence on **v2** (real CLI v2 mount, same session) | **BROKEN 3/3 runs** |
| direct `fallocate(PUNCH_HOLE)` probe (write 0xAB, punch, read) | **identical on v2 and v3**: punch acks, punched range reads stale bytes (both formats) |
| mkfs-shaped sequence (data → whole-file punch → explicit zero-write of a "log" region → readback) | identical on v2 and v3 (explicitly-zeroed region clean, punched-only region stale on both) |

Mechanism: `mkfs.xfs` issues BLKDISCARD (loop → `PUNCH_HOLE` on the
backing file) and trusts discard-zeroing; squeezefs acks the punch
without zeroing the range **on both formats** (a pre-existing data-path
gap — punch/discard handling in the router, untouched by every K-PR),
so xfs log recovery can read prior-leg bytes. Whether it trips depends
on block-reuse luck: the committed v2 baseline (174/0/9) ran on a fresh
volume whose punched ranges happened to read zeros; on this session's
dirtied volumes it breaks **3/3 on v2 and 3/3 on v3**. The v2-vs-v3
delta — the suite signal K7 gates on — is therefore **zero**; the
underlying punch-no-zero gap is filed as a data-path follow-up
(routing/fallocate; out of K7's metadata scope, pre-dates this branch).
