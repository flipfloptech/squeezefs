### Attribution (instrument, not product)

* The test was authored 2026-08-15 (`b8a9f615` / `b1371227`) on a box with
  **nvme-cli 2.16 / libnvme 1.16.1** (the laptop). libnvme implements
  `nvme read` on a char device as an `NVME_IOCTL_IO_CMD` passthru with an
  explicit nsid, which the controller char device honours for a
  single-namespace controller.
* `squeeze-test` has **nvme-cli 1.16-10.el8_10** (no libnvme). Reproduced on
  an isolated probe target (own NQN `…:werortype-probe-<pid>`, `127.0.0.1:54147`,
  torn down to zero residue) with `strace -e ioctl`:

  ```
  nvme read /dev/nvme30 -n 1 --start-block=0 --block-count=0 --data-size=512
    → rc=98, stdout 0 bytes, stderr empty
    ioctl(3, BLKSSZGET, …) = -1 ENOTTY (Inappropriate ioctl for device)
  nvme read /dev/nvme30n1 --start-block=0 --block-count=0 --data-size=512   (block node, control)
    → rc=0, "read: Success"
  nvme resv-register /dev/nvme30 -n 1 --nrkey=0x202600b --cptpl=0             (char device — the step that PASSED in the test)
    → rc=0, "NVME Reservation  success"
  ```

  i.e. nvme-cli 1.16's `nvme read`/`write` probe the device's block size with
  `BLKSSZGET` and bail silently (rc 98, no message) on a non-block node —
  exactly the `""` the test captured. The 1.x `resv-*` commands are passthru
  and work on the char device, which is why the test got as far as line 539.
* Everything the product did in that leg **succeeded** before the panic:
  `nvmeof share` (nvmet, resv_enable), `nvmeof connect` ×2 with explicit
  per-connection `--hostnqn/--hostid`, `NvmeReservationClient::register`,
  `acquire_write_exclusive_registrants_only`, and the device's Reservation
  Report echoing **rtype 3** (the assertion at the heart of the fix that this
  suite pins) — plus association B's `nvme resv-register` via its char device.
* **Out-of-gate manual verification of the pre-empted assertions** (same
  kernel nvmet, second isolated probe target `…:werortype-probe2-<pid>` on
  `127.0.0.1:54148`, driven with the 1.16-compatible `nvme io-passthru`
  opcode 0x02/0x01 through each association's char device; NOT acceptance

## How the gate was run (deviations from the stock invocation, all environmental)

The stock command `sudo tests/run_zc_capability_gate.sh` was wrapped
(`/scratch/tmp/sqz-agent/run-gate.sh`, launched via
`unshare -m --propagation private`) for three box-specific reasons; none
changes what the tests execute or assert:

1. **Root filesystem 100 % full** (`/dev/mapper/VolGroup00-LogVol01` 16 G,
   3.4 MB free — pre-existing; I removed nothing outside
   `/scratch/tmp/sqz-agent/`). It holds `/root` (=`$HOME`, where the zc
   suites create 2 GiB file-backed sandboxes under `$HOME/tmp`), `/tmp`
   (where `wero_rtype_tests` hard-codes its 64 MiB backing image) and `/usr`.
   Mitigation: `HOME=/scratch/tmp/sqz-agent/home`, `TMPDIR=/scratch/tmp/sqz-agent/tmp`,
   `RUSTUP_HOME`/`CARGO_HOME` under `/scratch/tmp/sqz-agent/`, and a private-
   namespace bind of `/tmp` → `/scratch/tmp/sqz-agent/tmp`.
2. **Live-mount protection.** The three zc suites' `Mount::drop` calls
   `abort_waiting_fuse_connections()`, which writes `abort` to **every**
   `/sys/fs/fuse/connections/*` with `waiting > 0` (cleanup only, never
   asserted on). Run as root that could sever the live 1.2.0 mount at
   `/scratch/tmp/test` (fusectl connection 51) mid-request. Mitigation:
   inside the private mount namespace, `/sys/fs/fuse/connections` was
   bind-shadowed with an empty directory (`ns-check: fusectl entries=0` in
   the log). Product code only touches fusectl under `--supervise`/`tune`,
   which these suites don't use. The live mount was checked before, during
   and after: daemon pid 849991 uptime 30 → 62 min continuous, `waiting=0`,
   `.stats` served, same commit `6e603a56`.
3. **No direct internet**; the box's dnf proxy `http://10.181.187.221:8888`
   reaches crates.io / static.rust-lang.org (verified with a real crate
   download), so `https_proxy`/`http_proxy` were exported for cargo/rustup.

Also: `SUDO_USER=root` was exported because I land on the box as root over
ssh (the gate's `run_as_user` then builds as root — acceptable for a
disposable checkout; the target/ is not shared with any dev build).

### `wero_rtype_tests` and the live fabric — assessed safe, run in-gate

Before running it I read the leg's setup and the product verbs it calls:
the test creates its own nvmet subsystem (`nqn.2026-08.io.squeezefs:werortype-<pid>`)
on `127.0.0.1:54146` (inside the 54100–54199 devsub slice) via
`squeezefs nvmeof share --target-stack nvmet`; port-id allocation skips
foreign ports, `nvmeof disconnect <nqn>` deletes only controllers whose

and link-free recorded ports. With explicit `--hostnqn/--hostid` it never
writes `/etc/nvme/{hostnqn,hostid}` (both pre-exist on the box, unchanged).
The live mount's 5-node fabric targets are **remote hosts**
(10.181.177.191–196 / 10.181.178.x, `trsvcid=4420`); the box had **no**
`/sys/kernel/config/nvmet` tree at all before the run (nvmet/nvmet-tcp were
not loaded — the test's `modprobe` loaded them; that is initiator-neutral).
So the leg was run in-gate rather than skipped.
