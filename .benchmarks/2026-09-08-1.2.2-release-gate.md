## 3. The finding run 1 produced, and the fix

`.benchmarks/2026-09-08-generic-795-lookup-wedge.md` has the capture and
the attribution. In one paragraph: inside `generic/795` (drop_caches ×
fsstress × rm/cp/cmp on a fresh mount) two delivered LOOKUPs on queue 16
were never COMMITted for 23 minutes; every one of the daemon's 205 threads
was idle — 32 queue workers parked UNBOUNDED in cq-wait, all handler lanes
parked — and fresh LOOKUPs on nine other CPUs' queues were never delivered
either. The class is the one the 2026-08-07 zc-bridge campaign closed for
zc pends with the bounded-outcome law (a 100 ms EXT_ARG-bounded worker
park while a pend lives, because "that chain CAN lose exactly one wake
under load"); an ordinary in-flight request had no bound. The wake's loser
(kernel task-work wake vs daemon) is NOT named: 48 fresh-mount storms with
the live capture armed did not recur.

Landed red-first (`8efc7e1b` → `1834bed4`): the worker's park is bounded
while its drain group owes any reply (`GroupHandle.owed`); a tick that
finds work a wake should have delivered is counted
(`transport_park_tick_{commit,cqe}_rescues`, ≈ 0 healthy — nonzero IS the
lost-wake tripwire) and the first rescue per worker, like the 5 s
overdue-slot WARN, carries the attribution snapshot (coalescer armed,
`eventfd-count`, ring `Sq/CqHead/Tail`, PollList entries). Seam
`SQUEEZEFS_TEST_DROP_COMMIT_WAKES`; suite `tests/commit_wake_loss_tests.rs`
— RED on the unfixed tree (the stat strands 3 s with the field posture;
the weakening check was reproduced independently by the release
engineer), GREEN with the fix (the stranded reply lands in one tick,
≈ 103 ms). The fstests runner gained the wedge verdict (`5a28c592`: a
delivered request unreplied ≥ 60 s is an UNEXPECTED FAILURE — replayed
RED on the real tape) so an abort-rescued test can never score clean
again.
