## Verdicts up front

1. **OQ 3 resolved: the README does NOT recommend SQPOLL — not even for dedicated metadata-heavy nodes — on this tip.** Post-M3 the queue worker's remaining `io_uring_enter` is the loop-bottom `submit_and_wait(1)` that *both* submits and waits; SQPOLL cannot delete it (the worker still has to park in `GETEVENTS`). What SQPOLL actually did: **+25 % enters/create (9.10 → 11.40)**, **one full core burned by the poller under storm (99.7–103 %)**, and **flat-to-worse paired mdstorm rows (−1.5 % create … −12.9 % mfunlink)**. The knob ships anyway — cheap, opt-in, deployment-shape-dependent — and the README says exactly what was measured.
2. **The syscall regression is de-coalescing, not extra work**: op shape is byte-identical off↔on (`fuse_ops`/op, `commit_sqes`/op, commit-carrying flushes/op, journal entries/op all equal to the third decimal). With the poller consuming SQEs the moment they are pushed, completions land at finer granularity and the worker's wake cycles fragment: 8.05 → 10.86 enters/create on the `fuse-over-uring-*` threads themselves, every one of them a `GETEVENTS` wait (raw-flag histogram: 238,667 of 238,670 enters carry `IORING_ENTER_GETEVENTS` alone; exactly **1** `SQ_WAKEUP` in the whole leg — the poller never sleeps under storm, so the "submit for free" benefit has nothing left to amortize).
3. **The one-poller policy holds by construction and by measurement**: knob-on adds **exactly one** `iou-sqp` thread on the tip (66 → 67 vs the pre binary; the 66 are the classical INIT/notify/sideband rings, which have honored these knobs since tokio.rs introduced them — pre-existing behavior, not this PR), and under storm **exactly one poller burns** (the shared queue-ring poller, 99.7 %; all 66 classical pollers stay at 0 % — their idle timeout parks them permanently after mount). Naive per-queue SQPOLL would have burned up to 32 cores; the ATTACH_WQ leader/follower topology bounds the cost at one, measured.
4. **Idle cost is zero on the quiet mount**: 60 s mounted-idle burns read 0.0 % poller and 0.0 % process on both sides (the 50 ms idle timeout parks all 67 pollers). The knob's cost is storm-time only — but storm-time is precisely when a metadata-heavy node wants its cores.
5. **No correctness movement anywhere**: `transport_parked_commits` 0, `fuse_over_uring_cqe_errors` 0, `transport_leases_outstanding` returns to 0, classical sideband alive (≈1.000/unlink — FORGETs by kernel mandate), journal shape byte-identical, clean unmounts, daemons exit bounded, single-writer guard refused a double-format during the session exactly as designed (D0 working as built).

## Syscall table — `sudo strace -c -f` on the caged daemon, 30 k ops × 8 threads per phase

Fresh volume + mount per side; strace attached for the phase window only; counts
are the signal (strace slows the daemon; ops/s in these legs are not rows).
Per-op = total calls / 30,000. Same tip binary both sides; the env knob is the
only delta.

| phase | syscall | SQPOLL off | SQPOLL on (idle=50 ms) | Δ |
|---|---|---:|---:|---:|
| **create** | **`io_uring_enter`** | **9.10** | **11.40** | **+2.30 (+25 %)** |
| create | `epoll_wait` | 15.49 | 15.67 | +0.18 |
| create | `futex` | 5.25 | 5.21 | −0.04 |
| create | `write` (eventfd wakes) | 19.19 | 19.28 | +0.09 |
| create | `read` (eventfd drains + sideband) | 12.10 | 14.43 | +2.33 |
| **stat** | **`io_uring_enter`** | **1.52** | **1.55** | +0.03 |
| **unlink** | **`io_uring_enter`** | **12.50** | **15.46** | **+2.96 (+24 %)** |
| unlink | `read` | 17.66 | 21.72 | +4.06 |

The `read` growth is the same fragmentation seen by the enters: more worker
wake cycles ⇒ more eventfd drains. The off-side column reproduces M3's
closing numbers (9.10 create / 12.5–12.6 unlink / 1.5 stat) to the second
decimal — same tip, same recipe, honest baseline.

**Idle-timeout sensitivity (create, knob on)**: idle=50 ms → 11.40; idle=1000 ms
→ **11.16** enters/create. Storm-time behavior is idle-insensitive (the poller
never sleeps mid-storm either way); the idle knob only chooses how fast the
poller parks on a quiet mount. There is no idle value that turns the +25 %
into a win.

| thread family | SQPOLL off (per create) | SQPOLL on (per create) |
|---|---:|---:|
| `fuse-over-uring-*` (32 queue workers) | **8.05** | **10.86** |
| `squeezefs-uring-fs-*` (8-worker pool) | 1.07 | 1.07 |
| main/other | 0.00 | 0.00 |
| **total** | **9.12** | **11.93** |

The entire regression is the queue workers whose rings got SQPOLL; the
`uring_fs` pool (no SQPOLL — its rings never read these knobs) is untouched at
1.07, and enter-flag histograms show all worker enters are pure `GETEVENTS`
waits on both sides (submission itself was already syscall-free post-M3 when
riding the wait; with SQPOLL it is syscall-free but the waits multiplied).

## Core-burn — `iou-sqp-*` CPU% (per-tid `/proc` utime+stime deltas)

| leg | pollers present | poller CPU | daemon process CPU |
|---|---:|---:|---:|
| off, mounted idle 60 s | 0 | 0.0 % | 0.0 % |
| on, mounted idle 60 s | 67 | **0.0 %** | 0.0 % |
| off, create storm (8 s window) | 0 | 0.0 % | 125.5–127.9 % |
| on, create storm (8 s window) | 67 | **103.0 %** | **224.0–225.1 %** |

Per-tid split under storm (`run_burnsplit.sh`): **exactly one** poller burning
— the shared queue-ring poller at 99.7 % — and all 66 classical-ring pollers
at 0 % (parked by their idle timeout; they only ever spin during mount setup).
Net: the knob converts ~+1 core (~+77 % daemon CPU) into *negative* throughput
on this box. The idle rows show the cost is storm-scoped: a quiet mount pays
only the 67 sleeping kernel threads' existence.

**Poller-population attribution** (knob ON): pre binary (dev @ `2f3fd90`,
queue rings SQPOLL-less) = **66** pollers — the classical `/dev/fuse`
INIT/notify/sideband rings, 2 per connection, which have honored these env
knobs since they existed (`tokio.rs`) — vs tip = **67** (= 66 + **the one**
shared queue-ring poller); tip with knob off = **0**. This PR's contribution
to the poller population is exactly +1, by construction (ATTACH_WQ) and by
count.

## OQ 3 verdict and the README text as landed

**Verdict**: on this tip (post-M3 submit economy), SQPOLL on the over-uring
queue rings has **no measurable benefit and a measurable cost** — the M10
mission's anticipated "one enter can already carry commit+wait" outcome, now
with numbers. The knob ships (it is cheap, opt-in, structurally bounded at one
poller, and deployment-shape-dependent by nature); the README documents the
knobs with the measured posture: **leave unset**; consider only on boxes with
uncontended spare cores where a live strace/`iou-sqp` profile of *your*
workload proves otherwise, and verify with exactly this session's counters.

## Deviations / notes for the record

1. **The classical rings already SQPOLL under these knobs (pre-existing, out of scope)**: setting `SQUEEZEFS_FUSE_IO_URING_SQPOLL_IDLE_MS` on a 32-CPU mount has always built one poller per classical `/dev/fuse` ring — 66 of them here (2 per connection). They cost nothing measurable (0.0 % idle and under storm; parked by idle timeout post-mount), but 67 kernel threads exist where a naive reading of "SQPOLL with idle timeout" expects 1. Recorded here and in the README posture note; restructuring the classical rings' SQPOLL topology is not M10 scope (M10's own queue rings share ONE poller by construction).
2. **The smoke's first two aborted runs left a daemon mounted** (script exited on a failed assertion before its unmount line); the D0 single-writer guard then refused the next format against the still-held volume — cleaned up by PID/unmount, smoke fixed, and a nice unplanned live exercise of the guard.
3. `sqm10pre` exists only for the poller-population attribution (the knob comparison itself is same-binary off/on, which is the stronger pairing); no pre-binary throughput rows were taken.
